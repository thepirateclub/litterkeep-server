# Задание для Terra: собственный почтовый сервер litterkeep на Rust

## Контракт выполнения: прочитать до первого изменения

Редакция: 19 сентября 2026 года. Профиль работы: агент с инструментами разработки, medium/high.

Название и уровень агента не определяют его API. Используй только реально доступные инструменты; не предполагай наличие особых функций Terra. Это задание для исполнения в рабочем репозитории, а не запрос написать ещё один план.

**Результат:** исходный код нашего сервера, собранный исполняемый файл, локальные тестовые ящики, независимые сетевые проверки и инструкция подключения litterkeep.

**Непересматриваемые решения:** Rust; один наш серверный процесс; собственные почтовые протоколы, MIME, хранилище и доставка; минимум низкоуровневых зависимостей; собственный оркестратор владельцев ресурсов и жизненного цикла задач. Никакой сборки из готовых почтовых проектов.

**Центральные инварианты:**

1. Каждый управляемый ресурс имеет владельца и ограниченный срок/условия использования. Реестр не заменяет реальное владение Rust.
2. Ожидающая задача не занимает отдельный исполнительный поток. Пробуждение происходит по событию, а не по циклу «проверить всё ещё раз».
3. Ожидание, отсутствие полезного прогресса и ошибка являются разными состояниями. IMAP IDLE не считается зависанием.
4. Таймаут инициирует отмену. Он не доказывает остановку владельца и не разрешает повторную выдачу занятого ресурса.
5. Входящая авторизованная сессия никогда не выдаётся другому клиенту. Пул применяется только к ресурсам с доказанным контрактом повторного использования.
6. Уже принятое письмо принадлежит долговечной очереди сервера, а не жизни клиентского соединения.
7. SMTP-успех и успех изменяющей IMAP/POP3-операции выдаются после нужной долговечной фиксации, не авансом.
8. Протокольная возможность объявляется только после реализации и проверки её семантики.
9. Нет неограниченных очередей, буферов, числа задач, потоков, подписок, таймеров и истории наблюдения.
10. Написано, собрано, запущено и проверено являются разными статусами. Не подменяй один другим.

Сначала достигни рабочего пути SMTP -> наше хранение -> IMAP -> проверенное вложение. Затем заверши оставшиеся обязательные протоколы и тесты. Оркестратор входит в первый путь, но разработка универсальной виртуальной машины, акторной платформы или аналога BEAM не входит в задание.

Это самостоятельное задание целиком заменяет прежние варианты. Оно сохраняет требование самописного Rust-сервера и добавляет согласованную модель надзора, ожидания и повторного использования ресурсов. Старую модель «один поток на каждую сессию» не переносить в окончательную реализацию. При конфликте со старым заданием руководствуйся этим документом и актуальными инструкциями репозитория, не ослабляя требования молча.

## 1. Задача и определение результата

Разработай на Rust самостоятельный почтовый сервер для клиента litterkeep. Напиши исходники, собери бинарный файл, запусти его в доступной локальной среде, создай тестовые аккаунты и письма, проверь работу независимыми сетевыми клиентами. При доступном litterkeep подключи и проверь именно его.

Требуется собственная реализация SMTP submission, входящего и исходящего SMTP, IMAP, POP3, MIME, Sieve, ManageSieve, файлового хранения, очереди доставки и восстановления. Протоколы должны обслуживаться нашим кодом, а не проксироваться или передаваться готовым движкам.

Пользователь ожидает исходный код собственного продукта, а не конфигурацию инфраструктуры, обёртку над библиотечным почтовым сервером, набор контейнеров или очередной архитектурный документ.

Первый полезный результат:

```text
litterkeep / Alice
    -> наш SMTP
    -> наше долговечное хранение и доставка
    -> наш IMAP
    -> litterkeep / Bob
    -> скачанное вложение с исходными байтами
```

Не откладывай этот сценарий до завершения POP3, Sieve и всех расширений. Но и не исключай их из конечной цели: промежуточный результат не равен завершению задания.

## 2. Жёсткие границы самостоятельной реализации

### 2.1. Что пишем сами

Нашему репозиторию принадлежат:

- сетевые декодеры и кодировщики команд, состояния сессий, проверка последовательности команд;
- серверная семантика SMTP, IMAP, POP3, ManageSieve и исходящий SMTP-клиент;
- разбор RFC 5322/MIME, заголовков, MIME-дерева, адресных полей и почтовых кодировок;
- управление аккаунтами, папками, флагами, UID, подписками и правами;
- файловое хранилище, журнал транзакций, индексы, очередь и восстановление;
- lexer, parser, AST, валидатор и исполнитель Sieve;
- CLI, конфигурация, тестовое наполнение и диагностика;
- оркестратор задач, реестр владения, выдача ресурсов, контроль прогресса, отмена, ожидание/пробуждение и пул исходящих соединений.

Почтовые протоколы реализуются по спецификациям. Не создавай собственный несовместимый вариант SMTP или IMAP ради простоты.

### 2.2. Что запрещено

Не использовать готовые почтовые серверы, их форки, встроенные движки или библиотеки, выполняющие перечисленную почтовую работу за нас. В частности, не подключать Postfix, Dovecot, Stalwart, James, Haraka, GreenMail, Mailpit или другие аналоги.

Не использовать production-зависимости типа lettre, mail-parser, mail-builder, imap-codec, imap-proto, готовый POP3/SMTP/Sieve framework. Не копировать исходники готового почтового проекта в `vendor/`, называя это самостоятельной реализацией.

Не использовать SQLite, RocksDB, sled, redb, SQLx, ORM, PostgreSQL, Redis или брокер сообщений. Для этого задания файловое хранение и его почтовые транзакции реализуем сами.

Не добавлять Tokio, async-std, mio, Actix, Axum, Tower, готовый actor/runtime framework, генератор парсеров, DI-контейнер, Serde, Clap, regex и отдельную библиотеку для каждой вспомогательной функции. Не строить собственный универсальный аналог этих библиотек: нужны небольшие компоненты под конкретную задачу.

Не добавлять Go, JVM, Node.js, Docker, Compose, Kubernetes, отдельный reverse proxy или внешний процесс, обязательный для работы сервера. Rust является выбранным языком, а не одним из вариантов.

### 2.3. Узкое исключение: TLS и криптография

Не реализовывать самостоятельно TLS, криптографические примитивы, генератор криптографической случайности, криптографическую проверку сертификатов и password hashing.

Предлагаемый allowlist прямых зависимостей серверного бинарника:

1. `rustls` для TLS с одним выбранным криптографическим backend;
2. `argon2` из RustCrypto для Argon2id и проверки хешей паролей.

Выбери минимально необходимые features по документации закреплённых версий. Не включай одновременно несколько криптографических backend без необходимости. Используй доступный безопасный генератор случайности криптографического provider, не timestamp, счётчик или собственный PRNG для паролей и солей.

Это НЕ требование «в Cargo.lock всего две строки». У TLS и криптографии есть транзитивные зависимости, а у backend могут быть C/assembler и инструменты сборки. Покажи их полностью. Не называй такой бинарник целиком pure-Rust или статическим без проверки. [RUSTLS], [CRYPTO], [ARGON2], [CARGO]

Для выпуска тестовых сертификатов допускается `rcgen` только как `dev-dependency` в `examples/make_test_pki.rs`. Не включай его в обычный серверный бинарник и не делай генератор сертификатов постоянно работающей службой. Это вспомогательная криптографическая операция разработчика. [RCGEN]

Для системного ожидания готовности сокетов разрешён один узкий собственный Linux FFI-модуль, описанный в разделе 7.2. Это обращение к ОС, не готовый runtime и не дополнительный почтовый пакет.

Другие прямые production-зависимости не добавляй молча. Зафиксируй необходимость и продолжай доступную работу без расширения разрешённого списка. Нельзя обходить запрет через `build.rs`, необъявленный внешний executable, FFI к готовому почтовому движку или загрузку кода во время запуска.

## 3. Формат поставки и ограничения первой версии

Один Cargo package с внутренними Rust-модулями. Допустимы `src/lib.rs` для тестирования и `src/main.rs` для CLI, но не workspace из десятков самостоятельных пакетов. Один основной исполняемый файл: `litterkeep-server`.

В runtime нужны только этот исполняемый файл, его обычные системные зависимости, конфигурация, сертификат с ключом и каталог данных. Компилятор Rust, Cargo, Python, генератор сертификатов и тестовый контрагент не должны требоваться для обычного запуска уже собранного сервера.

Первый подтверждённый профиль ориентирован на Linux и локальную файловую систему. WSL2 допустим при проверенной сетевой топологии и размещении данных на подходящей Linux-файловой системе. На Windows/macOS не заявляй проверенную долговечность только потому, что код компилируется. Не размещай рабочее хранилище на NFS/SMB или синхронизируемом облачном каталоге.

Публичная интернет-доставка не входит в первый локальный рубеж. SMTP-совместимость проверяется на локальном peer через обычный протокол. Отсутствие публичного DNS не является поводом не реализовывать исходящий SMTP.

## 4. Как работать с внутренним goal

Прочитай описание фактически доступного инструмента `goal`. Используй реальную схему, а не выдуманный вызов `goal.create(...)`. Создай корневую цель и подцели из раздела 19, с зависимостями, артефактами и критериями проверки.

Веди `GOAL.md`: идентификатор корневой цели, текущая подцель, зависимости, сделанные изменения, реальные команды, результат проверок, ограничения и следующий конкретный шаг. Обновляй внутреннюю цель после проверяемого результата. Не отмечай этап завершённым по наличию файлов или строк TODO.

Если `goal` отсутствует, обозначь это и веди те же этапы в `GOAL.md`; разработка продолжается. Если нельзя выполнить часть проверки, используй BLOCKED или NOT RUN, а не PASS.

Статусы: PASS, FAIL, BLOCKED, NOT RUN. UNSUPPORTED допустим только для явно необязательного расширения. Не называй обязательные POP3 или Sieve «неподдерживаемой опцией», чтобы закрыть цель.

Не проси повторно сведения, которые уже есть в репозитории. Не разрушай пользовательские изменения. При ограничениях среды сохрани реально работающую часть и точное состояние незавершённого, не подменяя реализацию новым планом.

### 4.1. Рабочий цикл агента

Разбивай этап на небольшие проверяемые изменения. Для каждого: прочитай существующий контракт -> добавь тест на нужное поведение -> реализуй -> запусти профильный тест -> проверь связанные сценарии -> обнови goal. Не проводи несколько несвязанных архитектурных переделок одновременно.

При обнаружении ошибки сначала воспроизведи её тестом. Не подгоняй ожидаемый результат под неправильный ответ сервера. Не меняй RFC-семантику ради зелёного теста.

Для medium/high-профиля используй явные чекпоинты: после каждого этапа записывай точные файлы, команды и оставшиеся условия. При продолжении сначала прочитай `GOAL.md`, `git diff` и выполненные тесты; не начинай проект заново. Не закрывай общую цель, когда готов только первый маршрут письма.

Если среда поддерживает дополнительных агентов, им можно поручать изолированные тесты, MIME-векторы или проверку протокола. Владельцы ядра runtime, модели хранения и общих контрактов должны быть определены заранее. Параллельные агенты не редактируют один и тот же контракт одновременно. Подзадача не считается принятой до интеграционной проверки. Наличие субагентов не обязательно.

Когда не хватает доступа к устройству, внешнему тестовому серверу или инструменту, продолжай независимые части. Реальный блокер запиши с точной командой и ошибкой. Не используй сложность задачи как причину заменить реализацию планом.

## 7. Обязательное ядро: оркестратор задач и ресурсов

### 7.1. Назначение и границы

Реализуй небольшой предметный оркестратор внутри нашего процесса. Он управляет реальными почтовыми сессиями, заданиями и ресурсами. Реестр, печатающий логи рядом с неуправляемыми потоками, не считается оркестратором.

Из Erlang заимствуется принцип supervision: явная иерархия, надзор за жизненным циклом, ограниченный перезапуск и наблюдаемое состояние. Не копируй BEAM, не называй это полным Erlang Observer и не обещай изоляцию памяти отдельных Erlang-процессов внутри общего Rust-процесса. [ERLANG-SUP], [ERLANG-OBS]

Минимальные обязанности: RootSupervisor, TaskRegistry, ResourceRegistry, Scheduler/Reactor, DeadlineManager, BudgetManager, OutboundConnectionPool. Это границы ответственности, а не требование отдельных сервисов или trait на каждое существительное.

### 7.2. Конкретная модель исполнения первого выпуска

Целевая платформа: Linux. Один серверный процесс, один сетевой reactor, небольшой фиксированный набор служебных потоков и ограниченные пулы для блокирующей работы. Сетевая сессия является структурой с FSM, а не OS-потоком.

Reactor владеет сетевыми дескрипторами и TLS-состояниями. Он обрабатывает готовность сокета, выполняет ограниченный шаг FSM и возвращается в диспетчер. Сессия, ожидающая сеть, commit или изменение ящика, сохраняет состояние и не занимает worker. Один последовательный владелец записывает ответы каждой сессии.

Практический backend первого выпуска: собственная минимальная обёртка над Linux `poll(2)` плюс неблокирующие сокеты `std::net`. Для локального лимита соединений этого достаточно как стартового решения. Вводить epoll, io_uring, work stealing или полноценный async runtime до измеренной необходимости запрещено. Не выдавай O(n)-обход массива poll за неограниченную масштабируемость. [POLL], [NET]

Стандартный неблокирующий TcpStream сам по себе не будит ожидающий диспетчер. Из-за запрета готового reactor crate допускается узкий FFI к `poll` в `src/platform/linux/poll.rs`:

- Проверь ABI именно целевой платформы по первичным документам. Используй корректные C-типы, `repr(C)`, проверенные размеры и диапазоны; не угадывай определения по чужой архитектуре.
- Безопасный публичный интерфейс принимает заимствованные дескрипторы, сохраняет их живыми на время вызова и не забирает владение чужим FD. Сокеты закрываются их владельцем, не произвольным кодом по числу FD.
- Явно обработай EINTR, ошибки, EOF, HUP и устаревшее событие. Готовность означает возможность попытки I/O, а не гарантию успешного полного чтения.
- В основном crate используй `deny(unsafe_code)` и локально разреши unsafe только этому модулю. Каждый unsafe-блок имеет проверяемый SAFETY-контракт. В почтовом ядре, парсерах, хранилище и оркестраторе unsafe запрещён. `forbid` на весь crate не ставить одновременно с этим исключением.
- Это единственное разрешённое отступление от safe Rust в нашем коде для первого backend. Не расширяй его на ручное управление буферами, криптографию или обход borrow checker.

Для пробуждения reactor при завершении работы, отмене или изменении расписания используй `UnixStream::pair()` в неблокирующем режиме либо столь же узкий безопасный механизм ОС. Очередь содержит событие, сигнал лишь будит обработчик. Несколько сигналов можно объединять. Переполненный канал пробуждения не разрешает потерять уже поставленное событие. [UNIX-STREAM]

Ожидание в ОС имеет таймаут до ближайшего deadline. Не делай периодическое чтение всех сокетов, `sleep(1ms)` или отдельный heartbeat-поток на задачу. Не держи writable-interest постоянно на пустом соединении: это создаёт холостой цикл.

Argon2, работа с файлами, fsync и тяжёлый MIME-разбор выполняются вне reactor, через ограниченные очереди. Writer метаданных один. Пулы ожидания диска/CPU конечны; их зависание не лечится бесконечным созданием новых потоков.

Для исходящего TCP connect в первой версии допустим ограниченный connector worker с `connect_timeout` и явным адресом из локального маршрута. Он возвращает TcpStream в reactor. Нет скрытого DNS-вызова, бессрочно блокирующего сетевой цикл. Собственный DNS/MX-resolver в этот выпуск не входит.

TLS обрабатывается шагами через API выбранного rustls с сохранением буферов и точного прогресса I/O. Уважай ограничения чтения/записи библиотеки. Проверь частичный TLS record, WouldBlock, close_notify, handshake timeout и ограничение буферов; не оборачивай reactor в бесконечный blocking complete_io. [RUSTLS-IO]

### 7.3. Типы, идентификаторы и регистрация

Используй отдельные типы TaskId, ResourceId, LeaseId, SessionId, JobId, Generation. Значения TaskId/ResourceId не являются адресами объектов или числом FD. При повторном использовании слота меняется generation; переполнение не приводит к молчаливому возврату старого значения.

TaskRecord содержит минимум:

```text
id + generation
parent / supervisor
kind и текущую предметную стадию
lifecycle state
wait set / wake reason
resource lease IDs
created_at, last_progress_at, stage_started_at
stage deadline / total deadline / cancel deadline
полезные счётчики продвижения
cancel status, retry/restart policy, последнее диагностическое событие
```

ResourceRecord содержит минимум:

```text
id + generation, kind
current owner либо явно перечисленные shared-read holders
state и лимиты
объём зарезервированной ёмкости
правило выдачи, возврата, закрытия и карантина
```

Регистрируй каждый управляемый долгоживущий или лимитируемый ресурс: TCP/TLS-сессию, исходящее соединение, открытый blob/spool handle, временный файл, подписку, timer/wait registration, worker permit, блок крупного буфера и разрешение на его память. Не регистрируй каждый локальный `&str` и элемент Vec: это реестр жизненного цикла, не собственный allocator.

Ресурс и запись реестра должны создаваться согласованно. При отказе регистрации закрывай уже созданный объект. После каждой выдачи, передачи, возврата и завершения можно проверить соответствие реестра фактическим владельцам.

Реестр хранит metadata, IDs и при необходимости Weak-ссылки, не дополнительные сильные ссылки, бессрочно удерживающие ресурсы. Завершённые записи удаляются или попадают в ограниченную историю. Следи за утечками самого оркестратора: таймеры, tombstones, отменённые waits и буферы событий тоже ограничены.

### 7.4. Состояния задачи отдельно от состояния ресурса

Пример базовых состояний задачи:

```text
Created -> Ready -> Running
Running -> Ready                     бюджет шага исчерпан
Running -> Waiting(WaitSet)           полезной работы пока нет
Waiting -> Ready                     наступило ожидаемое событие
Ready/Running/Waiting -> Cancelling   запрос отмены
Running/Cancelling -> Finishing -> Completed | Failed
```

Набор уточняй под реальный код, но переходы централизованы и протестированы. `Completed` невозможен, пока не разрешён вопрос владения дочерними задачами и ресурсами. Запрос отмены можно хранить ортогонально стадии, чтобы не потерять необходимое протокольное состояние.

Пример ресурса: Available -> Leased -> Returning -> Available; при ошибке Leased/Returning -> Quarantined -> Closed. Состояние Waiting у задачи не переводит её ресурс в Available.

Свободное соединение в пуле, IMAP-сессия в IDLE и SMTP-сессия с недополученным ответом являются тремя разными ситуациями. Не обрабатывай их одним idle-timeout.

### 7.5. Выдача ресурса: lease и владение

Реализуй типизированную выдачу временного владения, например ResourceLease<T>. Эксклюзивный lease не реализует Copy/Clone. Если ресурс допускает разделяемое чтение, у него отдельный контракт с учётом каждого держателя; это не основание разрешать совместную запись в TCP/TLS.

Lease перемещается вместе с работой. Передача другому владельцу обновляет ownership record и generation/операцию передачи так, чтобы старое завершение не могло освободить уже новую выдачу. Не отдавай наружу неучтённый Arc<TcpStream> или clone дескриптора.

Нормальный возврат в пул выполняется явно и потребляет lease. Протокольный слой выдаёт внутреннее подтверждение чистого состояния; произвольный вызывающий код не может изготовить его через публичные поля.

`Drop` является аварийной страховкой. Он не выполняет блокирующий сетевой reset, не ждёт свободного места в общей очереди и не паникует. Для несертифицированного сетевого ресурса безопасный default: закрыть/исключить из повторной выдачи. Изменение учёта возврата не должно теряться при переполнении telemetry: используй заранее зарезервированную запись завершения или прямое короткое безопасное обновление, а не best-effort лог.

Не пытайся вернуть lease через таймаут, пока работа ещё владеет объектом. Контроль доступа проверяет владельца и поколение, но проверка ID не заменяет реальное прекращение старой операции.

### 7.6. Событийное ожидание и безопасная пауза

Задача приостанавливается только на определённой безопасной границе, сохраняя минимальное состояние. WaitSet допускает ожидание любого из событий: readable, writable, completion, mailbox revision, available capacity, cancel, deadline.

При парковке освобождаются исполнительный слот и ненужные временные буферы, но сохраняются живое соединение, состояние TLS, протокольная стадия и обоснованно нужные данные. `Waiting` не означает нулевое потребление памяти. Политика сокращения памяти не уничтожает несохранённые байты.

Не парковать задачу с удерживаемым общим mutex или недокументированной блокировкой writer. Владение частным socket/TLS state допустимо: это не глобальная блокировка.

Переход проверка условия -> регистрация ожидания должен исключать lost wakeup. Используй счётчик версии события и повторную проверку после регистрации либо эквивалентный доказуемый порядок. Spurious wakeup допустим: после него условие проверяется заново. Один wake не должен ставить одну задачу в ready queue неограниченное число раз. [CONDVAR]

Если plaintext или разобранные команды уже лежат в буфере, не ждать нового TCP-события. Если исчерпан бюджет шага, ставить продолжение в ограниченную ready queue с сохранением справедливости. Не освобождать канал чтения, пока его downstream не может принять данные: управлять interest/backpressure, не накапливать всю почту в RAM.

Не добавляй команду «заморозить поток в любом месте». Административная pause, если её реализуешь, является кооперативным запросом на ближайшую безопасную границу; активная протокольная операция продолжает соблюдать свой deadline.

### 7.7. Полезный прогресс, сроки и отмена

Основной контроль идёт через события и счётчики, не через опрос «ты жив?». Heartbeat можно использовать для обнаружения неотвечающего executor, но он не сбрасывает deadline полезной работы.

Прогресс определяется стадией: реально принятые/выданные байты; завершённый parse stage; записанный chunk; подтверждённый commit; окончательный ответ адресата. Простой вход в цикл не является прогрессом. Для slowloris нужен предел всей стадии и отдельный stall/скоростной бюджет: один байт раз в минуту не продлевает приём бесконечно.

Используй монотонное время для внутрипроцессных интервалов и тестовый Clock для детерминированных сценариев. Для долговечной очереди отдельно храни перезапускаемые временные данные; не сериализуй `Instant` как время будущего запуска после рестарта.

Сроки handshake, AUTH, DATA, storage operation, idle pool connection и нормального ожидания IMAP задаются отдельно. Нормативные минимальные/рекомендуемые таймауты выбранного профиля не подменяй удобными короткими тестовыми. Тестовые ускоренные сроки имеют отдельную конфигурацию.

Последовательность отмены: установить запрос -> разбудить waits -> запретить новую работу -> дождаться cleanup/completion -> подтвердить освобождение -> решить возврат либо закрытие ресурса. Cancellation одного клиента не распространяется на чужие сессии и уже принятые сервером задания.

У каждого spawn есть зарегистрированный родитель и сохранённый join/result handle. Удаление JoinHandle не останавливает Rust-поток. Нельзя реализовать универсальный безопасный thread kill; зависший системный вызов и Argon2-вычисление не всегда прерываются немедленно. [JOIN]

Не выдавай permit повторно до фактического завершения такой работы. Если cancel deadline истёк: отметить Stuck/Quarantined, сохранить занятый лимит, прекратить увеличение пула и применить политику деградации. Критическая неопределённость writer требует остановить новые изменения и диагностировать сбой, не создавать второго writer параллельно. Не обещай гарантированное время graceful shutdown при непрерываемом syscall.

### 7.8. Передача ответственности от сессии к очереди

До принятия письмо и spool принадлежат операции приёма. При admission к writer передай commit-команду с содержимым и идентификатором в серверную область ответственности. После commit факт принятия не зависит от того, остался ли клиент подключённым. Ответ может оказаться недоставленным клиенту; это не основание удалить принятое письмо.

Если отмена пришла во время commit, определи фактический исход через ID транзакции и результат writer/recovery. Не угадывай по закрытию сокета. Сообщение при неопределённом исходе не принимается повторно как новое внутреннее задание без проверки.

Позднее completion для закрытой сессии сначала обрабатывает предметный результат и освобождение ресурса. Только UI/сетевой ответ можно отбросить по generation. Нельзя вместе с устаревшим ответом потерять факт долговечного commit.

### 7.9. Надзор и восстановление

Иерархия: root -> network/session tasks; root -> storage writer; root -> delivery jobs; root -> ограниченные CPU/I/O workers. Дочерний mail job после принятия принадлежит delivery supervisor, не session supervisor.

Ошибка соединения завершает эту сессию, а не перезапускает весь сервер. Безопасно воспроизводимый worker можно перезапустить после подтверждённого завершения и освобождения. Введи backoff и ограничение количества рестартов за окно. Не создавай бесконечный restart loop. [ERLANG-SUP]

Panic не является штатным управлением потоком. `catch_unwind` допустим только на осмысленной границе изолированной работы с описанными инвариантами; он не гарантирует целостность общего состояния. Ошибки writer или registry не маскируются попыткой «let it crash и продолжим». Panic=abort/авария процесса проверяются восстановлением хранилища, не мнимым завершением Drop.

Graceful stop: прекратить новый admission -> инициировать завершение сессий -> закончить/определить принятые commit -> оставить незавершённую доставку в долговечной очереди -> закрыть пул -> снять waits/subscriptions -> дождаться контролируемых workers -> закрыть journal и lock. Не пытайся синхронно доставить всю накопленную почту перед остановкой.

### 7.10. Диагностика и пределы самого надзора

CLI должен предоставлять `runtime stats`, `runtime tasks`, `runtime resources` и `runtime inspect <task-id>` через защищённый локальный control socket. Пример полей ответа: state, owner, held resources, wait reason, stage age, progress, deadline, cancellation. Без паролей, тела писем и закрытых ключей.

Метрики минимум: число tasks по состояниям; active leases по видам; ready/wait/completion depths; tracked/reserved buffer bytes; timers/subscriptions; inflight workers; open/idle/leased/quarantined connections; rejected admissions; deadline/cancel/restart counters; loop iterations и task steps без полезной работы.

Предусмотри фиксированное окно/кольцо диагностических событий и ротацию файлов. Завершённый TaskRecord не сохраняется навечно ради графика. Сервер не требует Prometheus, HTTP-панель или внешний collector.

Все лимиты конфигурируются. Для локального профиля задай и проверь, например, 64 клиентские сессии, 2 CPU workers, 2 I/O workers, 1 writer, максимум 2 исходящих соединения на маршрут и 8 суммарно. Это стартовые проектные значения, не гарантии производительности. Размер очереди ограничивается и числом элементов, и суммарными байтами; счётчики учитывают capacity, не только len. Argon2 memory cost и TLS buffers входят в отдельный документированный бюджет.

Память immutable сообщений и индексов может расти вместе с объёмом почты; тест утечки должен отличать полезное сохранённое состояние от потерянных ресурсов. RSS может не вернуться к стартовому значению из-за allocator/cache. Доказывай освобождение по live resources и bounded plateaus, а не обещанию «Rust вообще не течёт».

### 7.11. Общие правила Rust-кода

Автоматы оформляй enum и проверяемыми переходами; предметные ID отдельными типами. Не создавать `Arc<Mutex<Everything>>`, циклы сильных Arc или бесконтрольные `.clone()` для обхода владения. `Box::leak` и `mem::forget` не являются решениями lifecycle.

Используй Result и конкретные ошибки. Не допускай unwrap/expect/panic на сети, дисковых ошибках и пользовательском вводе. Тестовые assertions допустимы. Не раскрывай секреты через Debug.

Общие блокировки короткие, порядок захвата документирован. Реестр не держит lock при I/O или выполнении пользовательского Sieve. Прямое освобождение локального ресурса и публикация метаданных не должны зависеть от необязательной telemetry.

## 8. Собственное файловое хранилище

### 8.1. Модель

Не создавай универсальную БД. Нужен специализированный почтовый store:

```text
runtime/
  instance.lock
  server.conf
  tls/
  control/
  secrets/
  data/
    format-version
    journal/
      transactions.log
    messages/
      <внутренний-id>.eml
    tmp/
    checkpoints/       # последующий этап, не условие первого письма
```

Имена папок IMAP, email и имена вложений не превращаются в пути файловой системы. На диске используются только внутренние проверенные идентификаторы. Каталог принадлежит текущему пользователю и не допускает запись другими пользователями; не считать path sanitization защитой от атакующего, который уже может заменять файлы внутри него.

Сообщения хранятся неизменяемыми объектами. Метаданные, аккаунты, хеши паролей, папки, флаги, подписки, счётчики, версии Sieve и очередь восстанавливаются из журнала. Производные индексы можно перестроить; они не единственный источник истины.

Раздели MessageBlob и MailboxEntry. Флаги, UID и папка относятся к MailboxEntry, а не к общему содержимому. Один blob может иметь несколько ссылок. Message-ID из заголовка не является внутренним уникальным ID.

### 8.2. Запись и фиксация

Первой реализацией используй одного writer для всех изменяющих метаданные транзакций, получающего ограниченные сообщения от сессий. Фиксация SMTP-сообщения:

1. Принять байты в ограниченный временный файл, с проверкой размера.
2. Завершить нужное сохранённое представление сообщения без пересериализации его MIME-тела.
3. Синхронизировать временный файл, переименовать внутри той же файловой системы в уникальный неизменяемый объект, синхронизировать необходимые каталоги.
4. Записать один журналируемый transaction frame с созданием ссылки на объект и заданиями всех принятых получателей.
5. Синхронизировать журнал. После успеха опубликовать новое состояние и дать положительный ответ SMTP.

Имена blob создавать без перезаписи существующего файла; коллизия не разрешается заменой чужого сообщения. Не выполнять шаг 4 до долговечной публикации blob. При ошибке записи или синхронизации не отвечать успехом. При неопределённом состоянии writer останавливает приём изменений, а не продолжает писать поверх повреждённого хвоста.

Этот порядок является выбранной архитектурой проекта. `flush()` буфера и `sync_all()` не взаимозаменяемы; для публикации имён файлов на Linux отдельно учитывается синхронизация каталога. Не обещай защиту от отказа накопителя или нарушения им гарантий записи. [FILE], [FSYNC]

### 8.3. Формат журнала и восстановление

Опиши versioned binary framing: magic, версия, порядковый номер, transaction ID, длина payload, payload, контроль целостности и однозначный признак полного frame. Кодирование полей должно быть явным, с фиксированным endian, проверкой переполнений и максимальных длин.

Не записывай дамп памяти Rust-структуры. Не используй `DefaultHasher` как стабильный дисковый формат. Для обнаружения случайной порчи допустима небольшая собственная некриптографическая контрольная сумма с тестовыми векторами. Не выдавай её за защиту от злонамеренного изменения.

Recovery применяет только полные валидные транзакции в правильном порядке. Явно неполный хвост после последней целой транзакции обрабатывается отдельно от полной записи с ошибочной контрольной суммой. Последнюю и повреждение середины нельзя молча обрезать как «неуспевшие сохраниться данные».

Не сканируй весь файл в поиске следующего случайно совпавшего magic, продолжая обычную загрузку после нарушения целостности. При подтверждённой порче сохрани исходник и выдай диагностируемую ошибку. Исправление только отдельной явной командой, без обещания восстановления неизвестных байтов.

После recovery проверяй существование referenced blob. Объекты без зафиксированных ссылок могут остаться после аварии; они не доставляются автоматически. Уборка только offline после проверки достижимости, включая ссылки очереди. Не удаляй orphan-файлы на каждом запуске по одному возрасту.

Обычный restart восстанавливает те же папки, UIDVALIDITY, UID, флаги, активные скрипты и задания. Второй процесс записи в тот же data-dir должен получить отказ через удерживаемый OS file lock, а не через проверку существования PID-файла. [FILE]

Начальная версия может хранить журнал без online compaction. Добавь лимит дискового использования и offline checkpoint/maintenance последующим этапом. Не удаляй старый журнал до проверки долговечного checkpoint. Согласованный backup первой версии выполняется при остановленном сервере.

### 8.4. Атомарность почтовых действий

Одной транзакцией фиксируй изменения, которые должны быть неделимыми: добавление в папку и завершение локальной доставки; выделение UID и APPEND; перенос между папками; набор действий Sieve и завершение его задания; смена активной версии правила.

Внутренняя идемпотентность использует delivery ID + recipient/action ID. Повтор worker после аварии не должен второй раз добавлять письмо локальному адресату. Это не гарантия exactly-once для независимых SMTP-серверов.

UID выделяется в writer из сохранённого состояния конкретной папки. Не переиспользовать удалённые значения и не вычислять UID из позиции в Vec. Предусмотреть переполнение и недопустимость повторения эпохи UIDVALIDITY для повторно созданной папки. Правила идентичности сверять с [IMAP1], [IMAP2], [UIDPLUS].

Чтение большого blob не удерживает writer. Не считать `File::try_clone()` независимым файловым курсором: используй отдельное открытие либо подходящий позиционный read конкретной ОС. [FILE]

## 9. TCP, TLS, аутентификация и лимиты

Домены по умолчанию: `litterkeep.test` и для peer `peer.test`. Слушать только `127.0.0.1`, пока пользователь явно не включает LAN-профиль. `.test` не обеспечивает DNS автоматически.

Порты нашего процесса, без пробросов Docker:

| Порт | Назначение |
|---|---|
| 1465 | SMTP submission, TLS сразу |
| 1587 | SMTP submission, STARTTLS |
| 1993 | IMAP, TLS сразу |
| 1143 | IMAP, STARTTLS |
| 1995 | POP3, TLS сразу |
| 1110 | POP3, STLS |
| 14190 | ManageSieve, STARTTLS |
| 2525 | Входящий SMTP от разрешённого локального peer |

Всё конфигурируется. Сначала доведи защищённый путь на 1465/1993; затем реализуй остальные режимы. Не передавай пароль по незащищённому соединению даже ради первого smoke-test. Правила TLS для клиентского доступа не переносить бездумно на весь публичный межсерверный SMTP. [TLS-MAIL]

Наш сетевой код сам принимает и открывает TCP-соединения. Rustls обслуживает только TLS. Используй неблокирующую пошаговую интеграцию с reactor из раздела 7; сохраняй состояние при частичном I/O. Blocking StreamOwned допустим в независимом вспомогательном клиенте, но не как скрытый поток на каждую серверную сессию. [NET], [RUSTLS], [RUSTLS-IO]

Предусмотри границы TCP-фрагментов, склеенные команды, CRLF, literals и состояния передачи тела. Используй байтовые буферы. SMTP DATA и IMAP literal не обязаны быть UTF-8. Длина в протоколе считается в октетах.

STARTTLS является сменой режима и состояния. Предварительно прочитанные plaintext-команды нельзя выполнить после handshake. Немедленно пришедший ClientHello нельзя потерять вместе с буфером. Для каждого протокола выполни требуемые сброс состояния и обновление capabilities; у SMTP после STARTTLS выполняется новый EHLO. [SMTP-TLS]

Не повторяй целиком буфер после неоднозначной частичной записи. При ошибке отправки с неизвестным прогрессом закрывай сессию, не дублируй literal. Разрыв клиента не отменяет уже зафиксированную транзакцию.

Для TLS нужны свой тестовый CA, server certificate, правильные DNS/IP SAN. Генератор в examples выпускает их один раз; повторный запуск проверяет существующее и не заменяет CA без явной команды. Закрытый ключ CA не нужен `serve` и не передаётся клиенту. Проверяй доверие, hostname и срок сертификата. Не добавляй trust-all. [RCGEN], [TLS-MAIL]

Общий backend паролей обслуживает все протоколы. Соль и тестовые пароли генерируются криптографически; хранение пароля только в виде Argon2id, кроме отдельного защищённого файла с dev-реквизитами. Проверка хеша выполняется библиотекой. Проверяй authzid SASL PLAIN: свой пароль не должен давать право войти в чужой аккаунт. [ARGON2], [SASL]

Обязательны лимиты: соединения, незавершённые AUTH, размер команды/заголовков/DATA/literal, получатели, MIME-глубина/число частей, Sieve-размер/шаги, время handshake, I/O, размер исходящих буферов и дисковая квота. Значения по умолчанию документировать; для полного письма можно начать с 25 MiB. Не выделять память по недоверенной заявленной длине.

## 10. Собственный SMTP

Раздели SMTP submission и SMTP приём от peer политиками, не двумя копиями кода. На submission требуются TLS и AUTH; envelope sender принадлежит аккаунту или явно разрешённому алиасу. На peer-listener доставка в обслуживаемые локальные домены не требует пользовательского пароля. Ни один listener не становится open relay.

Напиши decoder, encoder, FSM и обработчики EHLO/HELO, MAIL, RCPT, DATA, RSET, NOOP, QUIT; предусмотренное стандартом поведение остальных базовых команд. AUTH и STARTTLS реализуются как расширения. Не включай фиктивное успешное выполнение VRFY/EXPN. [SMTP], [SUBMISSION], [SMTP-AUTH]

Состояния транзакции должны запрещать DATA без получателей, MAIL в недопустимой фазе, повторную аутентификацию в запрещённый момент. Отказ одного RCPT не уничтожает уже принятых адресатов. RSET очищает именно транзакцию, а не весь аккаунт.

Envelope и заголовки являются разными данными. Не доставляй по To/Cc вместо RCPT. Не дописывай всех скрытых получателей в служебные заголовки.

Поток DATA заканчивается протокольным терминатором; dot-stuffing снимается один раз. Не применять trim() к сообщению. Строго и последовательно обрабатывай bare LF и неоднозначные окончания тела на приёме и передаче.

Неизвестный локальный получатель и неразрешённый домен отклоняются на RCPT. Запрет внешней доставки действует и при действующих учётных данных. SMTP-успех после DATA разрешён только после принятия долговечной ответственности; затем тест отдельно проверяет доставку. [SMTP]

Сохраняй предусмотренные Received/Return-Path на соответствующих стадиях, не разрушая MIME-тело и не распространяя Bcc. SIZE, 8BITMIME и прочие EHLO-возможности объявляются после полноценной реализации. Не добавляй SMTPUTF8, CHUNKING, BINARYMIME, PIPELINING как декоративные строки.

Нужны тесты двух сообщений в одной сессии, разрыва DATA, неправильных порядков, частично принятых RCPT, ошибки sync, превышения размера, пустого reverse-path в корректном MTA-сценарии и потери финального ответа. Не обещай отсутствие дубля при повторе отправителем после неизвестного исхода.

## 11. Собственный MIME и почтовые кодировки

Напиши наш модуль разбора RFC 5322 и MIME без готового parser crate. Отдельно реализуй поиск границ заголовков, unfolding, structured headers, MIME parameters, multipart boundaries, Base64, quoted-printable, encoded words и продолжения параметров имени. Проверяй по [MESSAGE], [MIME1], [MIME2], [MIME-HDR], [MIME-PARAM].

Нельзя распознавать multipart простым поиском boundary как произвольной подстроки в содержимом. Учитывай строки разделителей, закрывающий delimiter, preamble/epilogue, вложенность и точные диапазоны октетов.

Поддержи text/plain, text/html, multipart/mixed, alternative, related, message/rfc822, Content-ID, неизвестный тип application/octet-stream. Не рендери HTML, не загружай удалённые картинки и не распаковывай вложенные архивы.

Raw-байты сохранённого сообщения остаются источником выдачи. Разобранное дерево хранит безопасные диапазоны исходника, а не новую сериализацию письма. Заголовки, повторения, переносы, имена и байты вложений не должны самопроизвольно переписываться при чтении.

Для декодированного поиска и Sieve реализуй начальные документированные charset-профили: US-ASCII, UTF-8 и ISO-8859-1. Дополнительные кодировки добавляй собственными небольшими таблицами с источником и тестами, если нужны клиенту. Неизвестный charset не должен превращать исходное письмо в повреждённый UTF-8: raw-доступ сохраняется, ограничения поиска явно отражаются.

Создай свои тестовые векторы и сравни результаты на независимом Python email parser. Не считай тест «наш encoder -> наш decoder» достаточным: оба могут одинаково ошибаться.

Для IMAP отдельно преобразуй разобранную структуру в ENVELOPE/BODYSTRUCTURE. BODY[part] возвращает требуемое представление части, а не произвольно декодированный файл. Частичные выборки считаются по октетам. Полное RFC822.SIZE относится к фактически выдаваемым байтам. [IMAP2], [IMAP-IMPL]

Вложения передаются внутри MIME. Не создавай обязательный HTTP endpoint загрузки вложения. Кириллица в тексте и имени файла должна работать без заявления поддержки международного email-адреса SMTPUTF8.

## 12. Собственный IMAP

Первый целевой профиль: IMAP4rev1 с действительно реализованными расширениями. RFC 9051 описывает rev2; rev1 выбран для начального профиля совместимости, а не назван новым стандартом. Не рекламируй rev2 или завершённую совместимость, пока их обязательная семантика не реализована. [IMAP1], [IMAP2]

Составь матрицу разделов базовой спецификации. Реализуй состояния и обязательные команды, а не только те, которые встретились в одной клиентской трассе. Первый узкий сквозной профиль допустим как явно экспериментальный.

Парсер: tag, atom, quoted string, escape, list, sequence set, literal и continuation. Он работает инкрементально и сохраняет состояние при любом разбиении входа. `split_whitespace()` не является IMAP parser.

Работы раздели на четыре очереди:

| Очередь | Покрытие |
|---|---|
| Вход и чтение | CAPABILITY, NOOP, LOGOUT, LOGIN/AUTHENTICATE, TLS, LIST, SELECT/EXAMINE, UID SEARCH, FETCH |
| Редактирование ящика | CREATE, DELETE, RENAME, SUBSCRIBE, UNSUBSCRIBE, LSUB, STATUS, APPEND, STORE, COPY, CLOSE, EXPUNGE, CHECK и UID-варианты |
| Корректная выборка | flags, INTERNALDATE, ENVELOPE, BODYSTRUCTURE, HEADER.FIELDS, MIME sections, PEEK, partial FETCH, базовые search keys |
| Расширения | IDLE, UIDPLUS, MOVE, SPECIAL-USE и их нормативные зависимости |

Перечень не заменяет базовую спецификацию. Нельзя успешно отвечать на неисполненный STORE или возвращать ложный пустой SEARCH вместо неподдержанного поведения.

Для rev1 реализуй modified UTF-7 имён, особый INBOX, delimiter, LIST wildcard и правила Recent. Не смешивай его с UTF-8-режимом rev2. Следуй правилам FLAGS/PERMANENTFLAGS/read-only и сохранению INTERNALDATE.

UID и порядковый номер в выбранной папке различаются. Идентичность клиента связывается с аккаунтом, папкой, UIDVALIDITY и UID. После удаления соседних сообщений не менять UID оставшихся. Снятие/установка Deleted и окончательное удаление являются разными операциями. [IMAP1], [IMAP2]

Раздельно проверь протокольную выдачу и сохранённое состояние. Ответ APPENDUID/COPYUID формируется из реально зафиксированных идентификаторов. UIDPLUS включает предусмотренные действия, а не только token в CAPABILITY. MOVE добавляется как цельная операция с верными изменениями источника и назначения. [UIDPLUS], [MOVE]

SPECIAL-USE не сводится к английским именам папок. Реализуй необходимые расширенные формы LIST и проверяй возвращаемые атрибуты. [SPECIAL-USE]

## 13. Одновременные сессии, IDLE, Sent и Drafts

Один и тот же ящик должен корректно обслуживать минимум две сессии для локальной приёмки. Сессия ведёт согласованное отображение sequence number -> запись папки. Не отправляй EXPUNGE в момент, когда стандарт запрещает изменение нумерации в текущем ответе. Используй нормативную семантику, а не произвольные callbacks writer. [IMAP-IMPL], [IMAP-MULTI]

События публикуются после фиксации. Запись literal и уведомления не перемешиваются. IDLE/DONE, очередь событий, завершение подключения и отставание подписчика тестируются отдельно. Переполненная очередь должна приводить к определённой ресинхронизации или контролируемому закрытию, не к неверным номерам. [IDLE]

При потере соединения не откатывай уже подтверждённые изменения и не выполняй скрытый EXPUNGE. После reconnect доступны те же сохранённые идентификаторы и флаги.

Политика нашего продукта: Sent сохраняет клиент через APPEND; сервер не создаёт ещё одну копию при submission. Drafts также сохраняется через APPEND и не отправляет письмо получателю. Создай INBOX, Sent, Drafts, Trash, Junk, Archive, Invoices и тестовую вложенную папку.

Сбой сохранения Sent после успешного SMTP не должен маскироваться повторной отправкой письма. В отчёте указывай раздельно доставку адресату и сохранение копии у отправителя.

## 14. Собственный POP3

POP3 использует тот же INBOX, а не отдельную коллекцию писем. Реализуй собственные состояния AUTHORIZATION/TRANSACTION/UPDATE, команды USER/PASS, STAT, LIST, RETR, DELE, NOOP, RSET, QUIT, UIDL, TOP, CAPA и STLS; implicit TLS тоже входит в итог. [POP3], [POP3-CAPA], [ACCESS-TLS]

UIDL устойчив между сессиями и не основан только на Message-ID. Размеры, dot-stuffing и окончания строк проверяются по выдаваемым байтам.

Выдели отдельный POP3 maildrop lease для конкурентных POP3-сессий. Зафиксируй политику снимка и конфликтующих IMAP-удалений. Не блокируй весь store на время TCP-сеанса и не теряй новую SMTP-доставку из-за долгой POP3-сессии.

Проверки удаления: DELE + RSET; DELE + disconnect до QUIT; DELE + QUIT и переход в UPDATE. Успешный QUIT требует соответствующей долговечной фиксации. Потеря ответа после начала UPDATE не должна превращаться в ложное обещание клиенту, что удаление точно не произошло.

Разрушающие тесты используют отдельный pop@litterkeep.test. Проверь согласованность с последующим IMAP и отсутствие самопроизвольного изменения флагов от скачивания POP3.

## 15. Собственный Sieve и ManageSieve

Sieve реализуй как язык, а не JSON-конфиг и не набор regex по теме письма. Наши стадии: lexer -> parser -> AST -> validation -> bounded execution -> DeliveryPlan -> транзакционное применение. Это устройство нашего движка, не отдельный сервис.

Составь покрытие базового RFC: require, if/elsif/else, stop; строковые формы и списки, комментарии; тесты true/false, allof/anyof/not, header/address/exists/size; match types/comparators; keep/discard/redirect и расширение fileinto. Учитывай implicit keep и сочетание действий. Неподдержанное require отклоняется. [SIEVE]

Исполнение не получает произвольного доступа к сети, файловой системе или shell. Все действия передаются почтовому ядру. Введи лимиты вложенности, количества узлов, операций и исходящих действий; исключи экспоненциальный matcher.

Фиксируй версию активного скрипта для конкретного задания. Replay после сбоя должен повторять тот же план либо безопасно переисполнять ту же версию. Fileinto, keep, очередь redirect и отметка завершения применяются согласованно. Runtime error обрабатывай по RFC, с предотвращением потери почты и доступной пользователю диагностикой, не только debug-log.

Redirect проходит общую политику маршрутов и ограничений циклов. Запрет внешней отправки нельзя обойти скриптом.

ManageSieve реализуется отдельным нашим listener по RFC 5804: framing, capabilities, TLS, SASL, управление и проверка скриптов. Нужны CAPABILITY, STARTTLS, AUTHENTICATE, LOGOUT, HAVESPACE, PUTSCRIPT, LISTSCRIPTS, SETACTIVE, GETSCRIPT, DELETESCRIPT, RENAMESCRIPT, CHECKSCRIPT, NOOP и корректные response codes. Не копировать механически IMAP literals. [MANAGESIEVE]

У скрипта владелец, имя, версия и квота. Ошибочная загрузка не заменяет действующий скрипт. Смена активности атомарна. Рекламируй только реально реализованные расширения Sieve.

Обязательное правило для заранее созданной Invoices:

```sieve
require ["fileinto"];
if header :contains "subject" "[invoice]" {
    fileinto "Invoices";
    stop;
}
```

Тест: загрузить правило через сеть, активировать, отправить SMTP-письмо, найти его через IMAP в Invoices. Контрольное письмо должно попасть в INBOX. Наличие текста правила на диске не является положительным результатом.

## 16. Наш исходящий SMTP и межсерверный обмен

Напиши исходящий SMTP-диалог на `std::net` и разрешённом TLS. Не использовать lettre, `sendmail`, `curl` или запуск другого MTA. Можно переиспользовать свои низкоуровневые кодировки, но не подменять независимые тесты тем же кодом.

Исходящий транспорт использует тот же lifecycle и собственный пул из раздела 16.1. Для локальной проверки запусти два экземпляра одного нашего бинарника с разными каталогами, доменами, портами и аккаунтами. Alice находится на litterkeep.test, Carol на peer.test. Разрешённые маршруты заданы явно: domain -> IP/host:port + TLS policy. Первый профиль допускает только локальные адреса peer и не запускает публичный MX-discovery.

Путь теста:

```text
независимый клиент -> submission экземпляра A
-> наш исходящий транспорт A -> SMTP экземпляра B
-> доставка B -> независимый IMAP-клиент
```

Затем такой же путь обратно. Отправка тестером напрямую в B не проверяет транспорт A.

Состояние очереди веди по адресатам: pending, in-flight, deferred, delivered, permanent failure либо эквивалентные типизированные состояния. Обработай многострочные ответы, частичные RCPT-отказы, таймауты, 4xx/5xx, восстановление после рестарта, ограниченные retries и срок жизни. Повторное выполнение локальных действий не дублирует их; удалённый неопределённый результат не скрывается.

TLS для локального peer проверяет выбранный CA и ожидаемое имя. Если peer не поддерживает требуемое кодирование/расширение, не передавай заведомо неподдержанное сообщение. Для первого выпуска допустим осмысленный постоянный отказ с недоставкой вместо непроверенного преобразования MIME.

Уже принятое письмо при окончательной ошибке не исчезает. Формируй корректное уведомление о недоставке для локального отправителя, не создавай цикл DSN на сообщение с пустым reverse-path. Поведение SMTP и DSN сверяй с [SMTP], [DSN].

Два собственных экземпляра не являются независимым доказательством совместимости. Отдельно проверь обмен с доступным сторонним тестовым MTA без включения его в продукт. При недоступности отрази NOT RUN. Не заявляй совместимость со всеми серверами и доставляемость в публичные ящики.

### 16.1. Пул исходящих SMTP-соединений

Пул переиспользует соединение после завершения SMTP-транзакции. Он не меняет принадлежность входящего IMAP/POP3/submission-соединения другому клиенту. Входящая сессия лишь возвращает исполнительное время диспетчеру. [SMTP]

Ключ пула включает маршрут/endpoint, ожидаемое TLS-имя, trust/policy version, TLS-режим и контекст аутентификации. Разные аккаунты/учётные данные не смешиваются. Изменение trust policy не оставляет старое соединение допустимым по новому ключу.

Одно соединение обслуживает не более одной исходящей транзакции одновременно. В пул возвращаются вместе TCP, TLS и SMTP FSM. Для возврата нужны полученные полные ответы, отсутствие незавершённого DATA, pending response и непрочитанных байтов, а также известная чистая протокольная стадия. Если для сброса нужен RSET, дождись его успешного ответа. Не выполнять RSET вслепую в середине неизвестной DATA-стадии.

Отмена, TLS-error, EOF, неожиданный ответ, неполный ответ после DATA и неизвестный результат передачи делают соединение непригодным к выдаче. Закрой его после прекращения владельца. Ошибка доставки сама по себе не всегда запрещает reuse: решение принимается по известному состоянию протокола, не только по классу 4xx/5xx.

Idle pooled connection не занимает worker, но сохраняет socket/TLS и ограниченную память. Зарегистрируй его на закрытие/входящий 421 и на idle TTL. Он не числится свободным после EOF. Перед повторной выдачей учти уже пришедшие ответы; отсутствие обнаруженного EOF не гарантирует успешность следующей операции.

Пинг NOOP необязателен. При реализации выполняй его как отдельную сериализованную операцию пула с ответом/deadline, не параллельно с почтовой транзакцией и не постоянно ради heartbeat.

Лимиты: global/per-route connections, число ожидающих выдачи задач, суммарная память, TTL простоя и максимальный возраст. При исчерпании пула job ожидает capacity/deadline/cancel. Уже принятое письмо остаётся в долговечной очереди; оно не теряется из-за переполнения RAM-очереди.

Различай «разбудить живое соединение» и «создать новое взамен закрытого». Для повторного connect нужны новый TCP/TLS handshake и новый протокольный контекст. Старый ResourceId/generation не воскресает.

При потере финального ответа после DATA фиксируй неоднозначный результат по адресату. Политика повторов должна прямо признавать риск удалённого дубля. Внутренний DeliveryId не обеспечивает exactly-once на чужом SMTP-сервере.

Обязательное доказательство reuse: отправь несколько сообщений подряд одному тестовому peer, который разрешает reuse; по server-side connection ID/счётчику accept докажи использование одного TCP-соединения после первого handshake. Само наличие класса Pool или сохранённого TcpStream не считается проверкой.

## 17. CLI, конфигурация и тестовые данные

CLI разбирается небольшим собственным кодом. Конфиг `server.conf` имеет явно описанную ограниченную грамматику `key=value`; не называть её полным TOML/YAML. Неизвестные ключи, конфликтующие поля, неправильные пути и порты должны давать понятные ошибки, а не молчаливые defaults.

Нужные команды с уточняемой, но документированной семантикой:

```text
litterkeep-server doctor
litterkeep-server init --data-dir ./runtime
litterkeep-server user add --data-dir ./runtime --email alice@litterkeep.test
litterkeep-server serve --config ./runtime/server.conf
litterkeep-server status --data-dir ./runtime
litterkeep-server stop --data-dir ./runtime
litterkeep-server seed --config ./runtime/server.conf
litterkeep-server check --data-dir ./runtime
litterkeep-server queue list --data-dir ./runtime
litterkeep-server runtime stats --data-dir ./runtime
litterkeep-server runtime tasks --data-dir ./runtime
litterkeep-server runtime resources --data-dir ./runtime
litterkeep-server runtime inspect TASK_ID --data-dir ./runtime
litterkeep-server backup --data-dir ./runtime --output ./backup
```

Это требования к создаваемому интерфейсу, не уже выполненные команды. Для Linux local control разрешён собственный минимальный Unix-domain socket через std, расположенный в каталоге с ограниченными правами. Он нужен только CLI-администрированию, не вместо SMTP/IMAP и не как новый обязательный протокол клиента.

Offline-команды берут тот же exclusive store lock. Никогда не открывай второй writer ради `user add` у работающего сервера. Для первой версии такие изменения допустимо разрешить только после остановки, явно сообщая об этом. `stop` использует local control, а аварийное завершение проверяется отдельно.

`init` повторяем: не меняет аккаунты, пароль, CA и почту. Создай alice@litterkeep.test, bob@litterkeep.test, qa@litterkeep.test и pop@litterkeep.test. Пароли генерируются один раз, не передаются аргументами команд и не выводятся в общий лог. `status` показывает endpoints и пути к локальным реквизитам, не содержимое секретов.

Seed использует сетевые протоколы: входящая почта через SMTP, исторические Sent/Drafts через APPEND. Его собственный SMTP-код допустим для наполнения, но не заменяет независимые тесты.

Начни с 5 писем, затем расширь до 30-50: русский/английский текст, emoji, HTML/plain alternative, ответы, пересылка message/rfc822, несколько получателей, Bcc, папки, флаги, вложенные MIME-структуры. Вложения: настоящий TXT, проверенный небольшой PNG, бинарный файл, пустой файл, Unicode-имя, несколько одинаковых имён и файл 10 MiB при подходящем лимите полного сообщения.

Не делай создание PDF/ZIP отдельной runtime-зависимостью. Дополнительные валидные fixtures допустимы как тестовые ресурсы с понятным происхождением.

Manifest содержит fixture ID, ожидаемого адресата, MIME-пути, имена, размеры и SHA-256 декодированных вложений. SHA-256 независимо считает тестовая среда; не нужно писать криптографический хеш ради этого в сервере.

Повтор seed не удваивает свои сообщения и не удаляет ручные письма. Для очистки идентифицируй только данные данного теста. Нельзя реализовывать глобальную SMTP-дедупликацию по Message-ID ради повторяемого seed.

## 18. Независимые проверки и подключение litterkeep

Production-сервер работает без Python. Для независимой проверки допускаются стандартные Python `smtplib`, `imaplib`, `poplib`, `email`, `ssl`, `hashlib`, `unittest`; они не входят в сервер и не подменяют его компоненты. Для ManageSieve сделай маленький независимый клиент без импорта нашего parser. [PYTHON]

Тесты используют уникальные run-ID, ограниченный общий deadline, выделенные ящики/папки и понятные коды завершения. Не ставь произвольные большие sleep вместо ожидания условия.

Отдельно тестируй codec units, FSM transitions, сетевые сессии, долговечность и реальный клиент. Генеративные тесты разбивают один и тот же вход по различным TCP-границам, склеивают команды, усекают literals и дают предельные длины. Fuzzing только против нашего тестового процесса. Fuzz-инструменты относятся к dev, не к production-зависимостям.

Нужны failpoints в тестовой сборке: запись blob, rename, directory sync, начало/конец frame, journal sync, публикация состояния, локальная доставка, выдача финального SMTP-ответа. Аварийный restart проверяет каждую границу. `kill -9` не выдавать за полное моделирование физической потери питания; дисковые short-write/error сценарии моделировать отдельно.

Для litterkeep предоставь host/port/TLS mode/login/CA и тестовые файлы. При доступном Android Emulator проверь адрес хоста 10.0.2.2; для USB можно использовать конкретные `adb reverse` только для нужных портов. Не утверждай, что hosts-файл компьютера действует на телефоне. При WSL/удалённом агенте проверяй реальную топологию. [ANDROID-NET]

Доверие тестовому CA добавлять только в debug-режим клиента и только способом, который реально использует его TLS-библиотека. Не отключать hostname verification и не менять release-доверие. [ANDROID-TLS]

Ручной путь: добавить Alice/Bob, отправить обычное письмо, ответить, выбрать файл в приложении, отправить, прочитать другим аккаунтом, скачать и сравнить файл, сохранить черновик, проверить Sent, папки, флаги и reconnect.

Результаты разделены на server-protocol, client-integration и manual-device. Успешный Python-тест не означает проверенную кнопку «Добавить вложение» в litterkeep.

Создай следующую последовательность подцелей. Каждый этап содержит реализацию и тесты, не только документацию. Допускается дробить подцели, не менять их обязательность.

| Этап | Что реализовать | Условие завершения |
|---|---|---|
| G00 | Обследование, Cargo, ограничения зависимостей, короткие контракты | Сборка, help, lock, отчёт зависимостей, сохранённый goal |
| G01 | Минимальный оркестратор, lease, registry, wait/wake, Linux poll, cancellation | Реальное ожидание/пробуждение сокета; нет потока на idle-сессию; тесты двойной выдачи и lost wake |
| G02 | Store, journal, blob, recovery, аккаунты, передача commit writer | Данные переживают рестарт; второй writer отвергается; commit не теряется при отмене |
| G03 | TLS, AUTH, admission/буферные лимиты, короткие FSM-шаги | Независимый TLS/AUTH, отказ плохим сертификатам/паролям, таймауты и освобождение ресурсов |
| G04 | SMTP submission и локальная доставка | Alice -> Bob, долговечное принятие, cleanup оборванной DATA |
| G05 | MIME и начальный IMAP, первый сквозной путь клиента | Отправка и чтение с проверенными вложениями; первый стабильный рабочий рубеж |

| G09 | Исходящий SMTP, собственный connection pool, retries/DSN | Обмен двух экземпляров и доказанный reuse; отменённые/грязные соединения не выдаются |

Основная цепочка зависимостей: G00 -> G01 -> G02 -> G03 -> G04 -> G05 -> G06. G07/G08/G09 выполняются после готовности нужных контрактов, затем общая интеграция G10-G12. Не ставь полный пул исходящих соединений, весь Sieve и сложный maintenance условием первого письма.

G01 должен дать минимальный работающий диспетчер и lifecycle, не универсальную инфраструктуру. Сетевой loop и состояние сессии развиваются вместе с SMTP/IMAP, но правила владения и отмены не оставляются «на потом».

После G05 обязательно запусти независимую отправку/чтение и зафиксируй рабочие команды. После каждого дальнейшего этапа повторяй этот smoke-test: новая подсистема не должна ломать уже работающую почту.

Недоступность телефона блокирует только ручную интеграцию. Недоступность чужого MTA блокирует только независимую межсерверную проверку. Не выдавай такие проверки за PASS и не останавливай все остальные работы.

### 20.1. Приёмка оркестратора: обязательные тесты

| ID | Сценарий | Что проверить |
|---|---|---|
| R01 | Acquire/transfer/release | В реестре один текущий владелец; реальный ресурс перемещён, не скопирован |
| R02 | Конкурирующий acquire | Один exclusive resource не выдаётся одновременно двум задачам |
| R03 | Timeout при живом владельце | CancelRequested есть, повторной выдачи и преждевременного освобождения permit нет |
| R04 | Двойной release и stale completion | Старый lease/generation не освобождает новую выдачу; нет двойного close |
| R05 | FD/slot reuse | Запоздалое событие закрытого FD не попадает в новую сессию с тем же номером |
| R06 | Lost wake в момент парковки | Событие между проверкой и регистрацией не теряется; задача завершает ожидание |
| R07 | Повторный/spurious wake | Условие перепроверяется; ready queue не раздувается дублями |
| R08 | Бездействующая сессия | Ждёт событие без worker/thread на сессию; нет постоянного runnable-цикла |
| R09 | IMAP IDLE и поступление почты | Сессия сохраняет владельца, просыпается и выдаёт корректное уведомление |
| R10 | Медленный читатель и полный downstream | Память/очереди ограничены; read/write interest не создаёт busy loop |
| R11 | Переполненный канал пробуждения | Поставленные completions и ownership transitions не теряются |
| R12 | Клиент ушёл до/во время/после commit | Различены непринятая DATA, принятая ответственность и потерянный ответ; нет потерянного письма |
| R13 | Worker не реагирует на cancel | Permit остаётся занятым; замещающие workers не размножаются; есть диагностика |
| R14 | CPU/Argon2 saturation | Ограничены одновременные операции и их память, другие сессии обслуживаются |
| R15 | Чистый SMTP reuse | Несколько последовательных писем используют одно соединение peer |
| R16 | Грязный/закрытый pooled connection | Неполный DATA-ответ, EOF, 421, TLS error исключают повторную выдачу |
| R17 | Изоляция ключей пула и ожидание capacity | TLS/auth contexts не смешиваются; ожидание отменяемо; лимиты соблюдены |
| R18 | Ошибка и перезапуск дочерней работы | Выполняются cleanup, предел рестартов и backoff; commit writer не дублируется |
| R19 | Graceful stop | Admission закрыт, завершение учтено, очередь сохранена, контролируемые threads joined |
| R20 | Churn и очистка самого реестра | После циклов нет роста retired tasks/timers/subscriptions/leases; история ограничена |

Тесты гонок выполняй детерминированно через barriers/управляемые точки остановки и тестовый Clock. Не надейся, что случайный `sleep` однажды попадёт в нужное окно. Нагрузочный прогон дополняет, но не заменяет эти тесты.

Ресурсный прогон для локальной машины: прогрев, затем не менее 10 одинаковых циклов по 100 подключений/разрывов с ограниченной одновременностью; отдельный прогон 32 одновременных IMAP IDLE-сессий; отправка/скачивание 10 MiB-вложения; серия deadline/cancel. Если ресурсы среды требуют уменьшить профиль, запиши фактические параметры и не выдавай уменьшенный тест за исходный.

После каждого цикла дождись quiescence с конечным deadline, запиши OS threads/FD/RSS и внутренние live tasks/leases/timers/subscriptions/buffer capacity. Полезную сохранённую почту не удаляй ради «нулевого RSS»: для lifecycle-теста используй один и тот же набор или отдельно учитывай его размер.

Условия: live-ресурсы возвращаются к документированному baseline с учётом разрешённого idle pool; ready/wait queues не накапливают мёртвые записи; после TTL пул освобождается; служебных потоков конечное число. RSS оценивается как ограниченное плато при одинаковом полезном состоянии, не как точное равенство первому замеру. Сохрани сырые измерения, не только слово «утечек нет».

Для проверки отсутствия busy loop запиши при бездействующих сессиях число task steps/событий/OS wakeups и CPU за измеренный интервал. Полное отсутствие любой активности не требуется: допустимы реальные дедлайны и служебные события. Постоянные шаги одной Waiting-задачи без причины являются FAIL.

Показывай реальные command/expected/actual/status/log. Не вписывай PASS вручную. Тест аварии не считается пройденным, если после неё пришлось удалить каталог и создать всё заново.

## 21. Документация и окончательная сдача

Нужны README, GOAL.md и содержательные документы: architecture, runtime-lifecycle, storage-format, protocol-coverage, dependencies, client-setup, security, acceptance; значимые решения сохраняются в decisions.md. Можно объединять близкие разделы, не создавать пустые шаблоны.

README должен позволять пройти путь от исходников до подключения клиента. Требуемая форма команд, уточняемая фактической реализацией:

```sh
cargo build --locked --release --bin litterkeep-server
cargo test --locked
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo run --locked --example make_test_pki -- ./runtime/tls
./target/release/litterkeep-server init --data-dir ./runtime
./target/release/litterkeep-server serve --config ./runtime/server.conf
# в другом терминале:
./target/release/litterkeep-server seed --config ./runtime/server.conf
python3 -m unittest discover -s tests/blackbox
```

Запиши фактический порядок настройки TLS-путей, запуска и наполнения; пример выше не должен скрывать отсутствующий шаг. Для первого создания Cargo.lock разрешена необходимая команда без --locked; после этого проверяй воспроизводимую сборку с lock.

Процесс агента и машина пользователя могут быть разными. Не называй удалённый localhost доступным пользователю без реального пути подключения.

В финале покажи путь к коду и бинарнику, реальные команды, endpoints, расположение CA/локальных реквизитов, результат T/R-тестов, реальные показатели runtime, реализованный профиль RFC и оставшиеся ограничения. Для каждого FAIL/BLOCKED/NOT RUN укажи конкретную причину. Приложи текстовый отчёт и машиночитаемый JSON/TSV из тестового раннера. Отдельно: написано, собрано, запущено, проверено протокольно, проверено в litterkeep.

Не выдавай локальный результат за production-ready. Публичный MTA потребует отдельного этапа: DNS/MX и политики маршрутов, доменная аутентификация, защита от злоупотреблений, нагрузка, эксплуатация, обновления и независимая проверка безопасности. Не добавляй эти компоненты в локальный запуск ради видимости полноты.
