# litterkeep-server

**Английская версия — [README.md](README.md).**

[![CI](https://github.com/thepirateclub/litterkeep-server/actions/workflows/ci.yml/badge.svg)](https://github.com/thepirateclub/litterkeep-server/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Самодостаточный почтовый сервер на Rust для локального профиля `litterkeep`.
Сервер реализует собственные протокольные парсеры, разбор MIME и Sieve,
файловое хранилище и оркестрацию задач и ресурсов. Готовые почтовые движки,
библиотеки протоколов и асинхронные рантаймы не используются.

**Сводная готовность проекта — [docs/ru/STATUS.md](docs/ru/STATUS.md).**
**Навигация по документации — [docs/ru/README.md](docs/ru/README.md).**

## Возможности

### Протоколы

| Протокол | Режимы | Состояние |
|---|---|---|
| SMTP submission | implicit TLS, STARTTLS | Основной путь доставки: `AUTH PLAIN`, `DSN` через EHLO, `MAIL RET`/`ENVID`, `RCPT NOTIFY`/`ORCPT`, DATA и BDAT |
| IMAP4rev1 | implicit TLS, STARTTLS | `LOGIN`, `AUTHENTICATE PLAIN` с SASL-IR, `APPEND`, `SELECT`/`EXAMINE`, `FETCH`, `SEARCH`, `STORE`, `COPY`/`MOVE`, `EXPUNGE`, `IDLE`, каталог папок, `STATUS` |
| POP3 | implicit TLS, STLS | `USER`/`PASS`, `RETR`/`DELE`, `UIDL`, аренда ящика писем |
| ManageSieve | STARTTLS | `AUTHENTICATE` с PLAIN, SCRAM-SHA-1, SCRAM-SHA-256 и SCRAM-SHA-256-PLUS; полный набор команд каталога скриптов; синхронные и фрагментированные литералы |

### Sieve

Рекламируемые расширения строго ограничены:
`fileinto subaddress envelope copy vacation vacation-seconds`.

Внутренне реализованы, но **не рекламируются** профиль RFC 5229 (`set`, проверка
`string`, раскрытие переменных в строках условий и действий, цели
`fileinto`/`redirect`, строки `vacation`, селекторы конверта и компаратора) и
декодирование RFC 5228 `encoded-character` (`${hex:...}`, `${unicode:...}`).
Строковые октеты сохраняются без потерь через лексер, сопоставление и действия
скрипта.

### Хранилище и доставка

- Файловый Store в формате `litterkeep-store-v2` с долговечными журналами и
  восстановлением после сбоя. Автоматической миграции с ранних форматов нет.
- Один владелец Store на процесс. Все входящие протоколы и исходящая доставка
  разделяют его.
- Исходящий планировщик с однопроходной доставкой, политикой повторов и
  локальным уведомлением отправителю после окончательного отказа.
- Сокет управления, оффлайн-проверка целостности и согласованное резервное
  копирование.

Полный профиль по каждому протоколу и проверенные границы описаны в
[docs/ru/protocol-coverage.md](docs/ru/protocol-coverage.md) и
[docs/ru/imap-profile.md](docs/ru/imap-profile.md).

## Требования

| | |
|---|---|
| Язык | Rust **1.97.0** (закреплён в `rust-toolchain.toml` и `Cargo.toml`) |
| Серверные ОС | Linux — реактор на `poll(2)` |
| Сборочная ОС | Любая, включая Windows: `fmt`, `clippy` и тесты выполняются там |

На Windows собирается и тестируется, но `serve` и остальные команды реактора не
запускаются и завершаются явным сообщением.

## Быстрый старт

### 1. Сборка

```sh
cargo build --locked --release --bin litterkeep-server
```

Единственный исполняемый файл сборки — `target/release/litterkeep-server`.

### 2. Инициализация каталога данных

```sh
cargo run --locked -- init --data-dir ./runtime
```

Команда создаёт локальные приёмочные учётные записи `alice`, `bob`, `qa` и
`pop`. Случайные пароли записываются в `./runtime/test-accounts.tsv` в формате
`<имя-учётной-записи><TAB><пароль>` без заголовка; на Linux файл получает права
`0600`. Секреты не печатаются в стандартный вывод. Повторный запуск проверяет
существующие записи и оставляет и файл паролей, и PHC-хеши байт-в-байт
неизменными.

Это локальная приёмочная инициализация, а не механизм управления учётными
записями.

Отдельная команда по явному запросу создаёт фикстуру получателя в Unicode для
приёмки SMTPUTF8 в отдельный файл `test-smtputf8-account.tsv`, не меняя
исходные учётные данные:

```sh
litterkeep-server init-smtputf8-test --data-dir ./runtime
```

### 3. Генерация тестового PKI

Сертификат и ключ задаются DER-файлами. Тестовый материал выпускается
одноразовой командой:

```sh
cargo run --locked --example make_test_pki -- ./test-pki
```

Клиент должен доверять выдавшему CA, а сертификат — содержать SAN с именем
хоста приёмника соединений. Для клиента с именем `litterkeep.test` в SAN должен
быть `litterkeep.test`.

### 4. Запуск

Режим STARTTLS для SMTP submission, IMAP и POP3:

```sh
cargo run --locked -- init --data-dir ./runtime
cargo run --locked -- serve-all-starttls \
  0.0.0.0:1587 0.0.0.0:1143 0.0.0.0:1110 \
  ./runtime ./server.der ./server.key.der
```

## Режимы запуска

Полный список команд с аргументами — `litterkeep-server help`.

### Один процесс со всеми входящими протоколами

SMTP submission, IMAP, POP3 и ManageSieve в одном реакторе с одним владельцем
Store. Рукопожатие TLS завершается до выдачи любого протокольного приветствия,
поэтому учётные данные не передаются открытым текстом.

```sh
cargo run --locked -- serve-all-mail-starttls \
  0.0.0.0:1587 0.0.0.0:1143 0.0.0.0:1110 0.0.0.0:4190 \
  ./runtime ./server.der ./server.key.der
```

### Неявный TLS (implicit TLS)

Один процесс с SMTP submission, IMAP, POP3 и ManageSieve поверх неявного TLS.
Порты по умолчанию привязаны к локальному интерфейсу:

```sh
cargo run --locked -- serve-all-mail-tls \
  127.0.0.1:1465 127.0.0.1:1993 127.0.0.1:1995 127.0.0.1:14190 \
  ./data ./data/pki/server.der ./data/pki/server.key.der
```

[RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html) описывает неявный TLS
для SMTP submission, IMAP и POP3. Неявный TLS для ManageSieve здесь является
дополнительным режимом запуска сервера, а не утверждением о нормативном порте
или требовании RFC 8314. Команда не заменяет существующие приёмники соединений
с STARTTLS и сама по себе не означает полной совместимости протоколов.

### Только SMTP и IMAP

```sh
# открытое приветствие с обязательным переходом на TLS
cargo run --locked -- serve-starttls 0.0.0.0:1587 0.0.0.0:1143 ./runtime ./server.der ./server.key.der

# неявный TLS
cargo run --locked -- serve-tls 0.0.0.0:1465 0.0.0.0:1993 ./runtime ./server.der ./server.key.der

# базовый режим без TLS
cargo run --locked -- serve 127.0.0.1:2525 127.0.0.1:2143 ./runtime
```

### Только POP3

```sh
cargo run --locked -- serve-pop3-starttls 0.0.0.0:1110 ./runtime ./server.der ./server.key.der
cargo run --locked -- serve-pop3-tls 0.0.0.0:1995 ./runtime ./server.der ./server.key.der
```

Клиент обязан выполнить STLS до `PASS` на порту 1110 либо использовать неявный
TLS на порту 1995. Приёмочная учётная запись POP3 — `pop`, её пароль лежит в
`test-accounts.tsv`.

### Только ManageSieve

```sh
cargo run --locked -- serve-managesieve-starttls 0.0.0.0:4190 ./runtime ./server.der ./server.key.der
```

## Исходящая доставка

### Маршрут STARTTLS

```sh
litterkeep-server serve-all-mail-outbound-starttls \
  0.0.0.0:1587 0.0.0.0:1143 0.0.0.0:1110 0.0.0.0:4190 \
  127.0.0.1:2526 ./data/g09-live server.der server.key.der
```

### Маршрут неявного TLS

Для постоянного маршрута с неявным TLS используется отдельная команда: адрес,
проверяемое имя и CA закрепляются за отдельным пулом соединений и не смешиваются
с открытым текстом.

```sh
litterkeep-server serve-all-mail-outbound-tls-starttls \
  0.0.0.0:1587 0.0.0.0:1143 0.0.0.0:1110 0.0.0.0:4190 \
  127.0.0.1:2465 peer.test peer-ca.der ./data/g09-live \
  server.der server.key.der
```

Повторное использование соединения разрешено после успешного DATA или
подтверждённого RSET. Обрыв соединения, таймаут, ошибка TLS и отказ RSET
уничтожают соединение. Проверка на Linux дополнительно проводит этот маршрут
через постоянный планировщик: доверенный SAN завершает долговечную доставку, а
неверный SAN оставляет задание в состоянии `Deferred`, переживающем перезапуск,
вместо потери письма или повторного использования соединения с TLS.

### Таймауты фаз RFC 5321

Исходящий SMTP с TLS использует фазовые таймауты RFC 5321. Они настраиваются
положительными целыми секундами при старте процесса:

| Переменная | Фаза | Значение по умолчанию |
|---|---|---:|
| `LITTERKEEP_SMTP_GREETING_TIMEOUT_SECONDS` | приветствие | 300 |
| `LITTERKEEP_SMTP_COMMAND_TIMEOUT_SECONDS` | обычная команда, MAIL, RCPT | 300 |
| `LITTERKEEP_SMTP_DATA_START_TIMEOUT_SECONDS` | ответ на DATA | 120 |
| `LITTERKEEP_SMTP_DATA_BLOCK_TIMEOUT_SECONDS` | каждая системная запись блока DATA | 180 |
| `LITTERKEEP_SMTP_DATA_FINAL_TIMEOUT_SECONDS` | финальный ответ после terminator | 600 |

```sh
LITTERKEEP_SMTP_GREETING_TIMEOUT_SECONDS=300
LITTERKEEP_SMTP_COMMAND_TIMEOUT_SECONDS=300
LITTERKEEP_SMTP_DATA_START_TIMEOUT_SECONDS=120
LITTERKEEP_SMTP_DATA_BLOCK_TIMEOUT_SECONDS=180
LITTERKEEP_SMTP_DATA_FINAL_TIMEOUT_SECONDS=600
```

Незаданные значения используют значения по умолчанию из RFC. Некорректный или
нулевой таймаут отклоняется при старте исходящего воркера. Таймаут ввода-вывода
уничтожает грязное соединение, долговечное задание переводится в политику
повторов, а соединение не возвращается в пул.

### Ограничения маршрута

Маршрут принимает только явный числовой `IP:port`. Это исключает скрытое
блокирующее разрешение имён внутри воркера доставки. Установка соединения
ограничена пятью секундами.

Первый фиксированный профиль маршрутов разрешает перенаправление Sieve только в
типизированный домен `peer.test`. Адрес проверяется при построении плана
доставки и повторно в воркере доставки до открытия сокета. Запрещённый маршрут
применяет неявное сохранение и пишет диагностику Sieve, а повреждённое задание
в очереди получает терминальный код `5.7.1` вместо бессмысленных повторов.
После восьми полей `Received` в трассировке новое перенаправление также
заменяется неявным сохранением, что ограничивает межсерверную петлю.

### Разовый проход очереди

```sh
litterkeep-server queue-drain ./data/g09-service-blackbox 127.0.0.1:3555 1
```

Команда владеет одним ограниченным воркером Store и одним ограниченным воркером
исходящего SMTP. Она фиксирует `InFlight` до SMTP, ждёт сокеты пробуждения
воркера, записывает терминальное долговечное состояние и публикует локальное
уведомление отправителю после окончательного отказа.

Исходный сервер должен быть остановлен: Store намеренно допускает только одного
писателя. Это явный ограниченный проход для диагностики и восстановления.
Обычная сервисная доставка использует `serve-all-mail-outbound-starttls`,
планировщик которого разделяет владельца Store и маршрутизацию пробуждения с
входящими протоколами. Каждый запрос к Store, задание доставки и таймер
ожидания представлены реальной версионированной записью в общем оркестраторе и
видны через `runtime tasks` и `runtime stats`.

## Обслуживание и диагностика

### Сокет управления

```sh
litterkeep-server runtime stats --data-dir /data
litterkeep-server runtime tasks --data-dir /data
litterkeep-server runtime resources --data-dir /data
litterkeep-server runtime inspect 2:1 --data-dir /data
litterkeep-server runtime cancel 2:1 --data-dir /data
```

Сервер владеет локальным сокетом Unix-домена в своём цикле опроса и возвращает
только метаданные жизненного цикла: состояние задачи, защищённые поколением
идентификаторы и удерживаемые ресурсы. Тела писем, пароли и ключи TLS не
возвращаются. Сокет находится во временном каталоге процесса, а его имя задаёт
указатель `/data/runtime.control`, доступный только владельцу. Такой подход
исключает зависание `bind(2)` на общих каталогах Docker Desktop. Перед
подключением программа проверяет, что указатель остаётся внутри временного
каталога.

Команда `cancel` переводит задачу в кооперативную отмену. Для клиентской сессии
реактор закрывает фактически принадлежащий ей сокет через единый путь очистки.
Исходящий планировщик в простое завершается сразу, а при активной доставке
сохраняет владение до завершения текущей операции SMTP и её долговечного
перехода, затем закрывает канал воркера, выполняет `join` и удаляет метаданные
жизненного цикла. Активный сокет SMTP командой `cancel` не прерывается:
ожидание ограничено таймаутом текущей фазы, который может составлять до 600
секунд. Команда не освобождает чужой или ещё используемый ресурс авансом.

### Проверка целостности

```sh
litterkeep-server check --data-dir ./data
```

Оффлайн-проверка берёт эксклюзивную блокировку Store, выполняет штатное
восстановление незавершённых записей и читает каждый файл сообщения, на который
ссылается mailbox или ожидающая исходящая доставка. Потерянные файлы сообщений
только подсчитываются и не удаляются.

### Резервное копирование

```sh
litterkeep-server backup --data-dir ./data --output ./data-backup
litterkeep-server check --data-dir ./data-backup
```

Согласованная копия разрешена только при остановленном владельце Store. Каталог
назначения должен отсутствовать и не может находиться внутри исходного каталога.
Команда копирует постоянные данные, синхронизирует копию и сама запускает
проверку.

### Диагностика Sieve

```sh
litterkeep-server sieve-errors ./data/g08-sieve-diagnostics bob
```

Команда оффлайн: она открывает Store как единственного писателя и потому не
должна запускаться параллельно с сервером. Каждая строка содержит транзакцию
доставки, учётную запись, фактически исполненную версию скрипта и типизированный
код ошибки.

Если ограниченный исполнитель Sieve отклоняет уже активную версию во время
доставки, сервер применяет неявное сохранение и не публикует частично накопленные
перенаправления или действия `fileinto`. Журнал диагностики ограничен 1 MiB;
исчерпание квоты отклоняет транзакцию до успеха SMTP, а не принимает письмо без
обещанной диагностики.

### Наполнение тестовых ящиков

```sh
litterkeep-server seed 127.0.0.1:1465 127.0.0.1:1993 litterkeep.test \
  ./ca.der alice ./alice.password ./bob.password ./qa.password
```

Первая сетевая контрольная точка наполнения использует SMTP submission с неявным
TLS и IMAP `APPEND`. Пароли читаются из файлов и не попадают в аргументы
процесса. Повторный запуск ищет только собственные `X-Litterkeep-Fixture` в
целевых папках, поэтому не удваивает фикстуры и не удаляет ручную почту.

Ожидаемый состав и SHA-256 декодированных вложений записаны в
`tests/fixtures/seed-manifest.tsv`. Полный набор содержит 35 писем и включает
текст, Unicode, эмодзи, ответы, `message/rfc822`, HTML-альтернативу, папки
Sent, Drafts и Archive, флаги и восемь вложений, в том числе точное вложение
10 MiB.

## Подключение почтового клиента

Для локального профиля с STARTTLS укажите в litterkeep полный адрес учётной
записи, например `alice@litterkeep.test`, один сгенерированный пароль из
`test-accounts.tsv` и следующие адреса подключения:

```text
IMAP host: localhost, port: 1143, mode: STARTTLS
SMTP host: localhost, port: 1587, mode: STARTTLS
Trust anchor: ca.pem из инициализированного тестового PKI
```

При подключении физического Android-устройства через USB перенаправляются только
нужные приёмники соединений:

```powershell
adb reverse tcp:1143 tcp:1143
adb reverse tcp:1587 tcp:1587
```

Для Docker порты на хосте могут отличаться. Неизвестный CA должен быть сначала
отклонён; затем CA выбирается в штатном диалоге litterkeep. Сервер нормализует
полный локальный адрес во владельца учётной записи, но не принимает внешний
домен.

Вывод IMAP IDLE ограничен по объёму на соединение. Если отдельный подписчик
перестаёт читать и превышает этот предел, отзывается только его аренда сессии;
реактор и остальные подписчики mailbox продолжают работать со своими
согласованными проекциями. После переподключения клиент должен заново выполнить
SELECT, чтобы получить свежий список номеров последовательности.

Фактический статус устройства и ограничения интерфейса зафиксированы в
[docs/ru/client-setup.md](docs/ru/client-setup.md).

## Ограничения ресурсов

| Ограничение | Значение |
|---|---|
| SMTP DATA и ответ IMAP | 25 MiB |
| Бюджет неизменяемых файлов сообщений на каталог данных | 25 MiB |
| Журнал диагностики Sieve | 1 MiB |
| Время ожидания операции Store | 5 минут |

Бинарное вложение размером 10 MiB помещается после MIME-кодирования в base64.
Единственный писатель хранилища восстанавливает фактическое использование при
старте и отклоняет новое письмо до создания временного файла, если бюджет был бы
превышен.

Текущий маркер на диске — `litterkeep-store-v2`. Автоматической миграции с более
ранних форматов разработки нет: неизвестный или непомеченный каталог данных с
почтой отклоняется.

## Разработка и проверка

```sh
cargo build --locked --release --bin litterkeep-server
cargo test --locked
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo run --locked -- help
cargo tree --locked -e normal
```

Тот же набор выполняется в CI на каждом пуше: `fmt` и `clippy` на ubuntu и
windows, тесты на ubuntu и windows, плюс релизная сборка.

Черновые проверки чёрным ящиком лежат в `tests/blackbox/`. Они используют только
стандартные клиенты Python и требуют живого сервера. Docker здесь является
исключительно проверочным окружением, а не обязательной частью `litterkeep-server`.

Примеры проверок:

```sh
# TLS submission с вложением
python tests/blackbox/tls_smtp_auth_attachment.py

# POP3: доставка, чтение и пустой ящик писем, с переиспользованием одного каталога
python tests/blackbox/pop3_starttls_delivery.py --phase smtp --port 11587 --ca ./data/pki/ca.pem
python tests/blackbox/pop3_starttls_delivery.py --phase pop3 --port 11110 --ca ./data/pki/ca.pem
python tests/blackbox/pop3_starttls_delivery.py --phase empty --port 11110 --ca ./data/pki/ca.pem

# ManageSieve: активация fileinto и доставка до IMAP
python tests/blackbox/managesieve_literal_delivery.py \
  --smtp-port 1587 --imap-port 1143 --managesieve-port 4190 --ca ./data/pki/ca.pem
```

Проверки на Linux хранят артефакты этапов под `./data`; если привязанный ввод-вывод
Docker Desktop недоступен, тот же этап использует контейнерный `/data` и явно
фиксирует это ограничение. Общий тестовый PKI лежит в `./data/pki`. Все эти
локальные артефакты игнорируются Git и исключены из контекста сборки образа.
Они восстанавливаются: `init` пересоздаёт приёмочные учётные записи, а
`make_test_pki` — тестовый PKI, поэтому `data/`, `runtime/`, `runtime-smoke-*/` и
каталоги PKI для верификации можно удалять между прогонами.

## Структура проекта

```text
src/            исходный код сервера, по одному модулю на профиль
  platform/     единственные небезопасные границы: poll(2) и flock(2)
  reactor/      реактор опроса Linux, сессии, планировщик исходящей доставки
  storage_worker/  единственный владелец Store
  store/        файловый Store, журналы, восстановление
  smtp/ imap/ pop3/ managesieve/  протокольные парсеры и машины состояний
  sasl/         SCRAM, Argon2id, собственные SHA-1/SHA-256/HMAC/PBKDF2
  mime/         MIME, декодирование кодировок, структура сообщения
  sieve/        парсер Sieve и ограниченный исполнитель
docs/           документация проекта, вход — docs/README.md
tests/          модульные, интеграционные и проверки чёрным ящиком
tools/          генераторы таблиц Unicode и кодировок
docker/         образ Linux-окружения для проверок
examples/       make_test_pki и вспомогательные инструменты
```
